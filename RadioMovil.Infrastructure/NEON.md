# Neon — configuración operativa

- Proyecto vinculado mediante `.neon`; `neon.ts` declara solo Postgres. `neon deploy` sobre `production` descargó `DATABASE_URL` y `DATABASE_URL_UNPOOLED` a `.env.local` (ignorado por Git).
- ASP.NET Core usa Npgsql + EF Core; en `Production` admite `DATABASE_URL` del proceso y exige TLS VerifyFull. `.env.local` no se carga automáticamente en procesos .NET: el hosting debe inyectar `DATABASE_URL` como variable de entorno. `/health` verifica la API, no la conexión a la base.
- En `Development`, la API acepta `NEON_DEVELOPMENT_CONNECTION_STRING` o `NEON_DEVELOPMENT_DIRECT_CONNECTION_STRING` de su proceso; `/health/db` consulta la tabla `solicitudes` y devuelve 503 cuando falta la conexión o la consulta falla. No ejecuta migraciones ni escrituras.
- Esta aplicación .NET necesita alojamiento ASP.NET Core independiente: `neon deploy` configura Postgres, **no publica ni inicia la Web API**.

- Crear ramas aisladas: `development` y `testing` (esta última a partir de development migrada). Nunca usar production como origen de pruebas.
- Proporcionar conexiones mediante variables de entorno o secretos externos, nunca en `appsettings*.json` ni en Git.
- `NEON_DEVELOPMENT_CONNECTION_STRING`: API en entorno `Development`.
- `NEON_DEVELOPMENT_DIRECT_CONNECTION_STRING`: herramientas de migración EF **solo** contra la rama development autorizada.
- `NEON_TESTING_CONNECTION_STRING`: API en entorno `Testing`.
- `NEON_TESTING_DIRECT_CONNECTION_STRING`: pruebas de integración, rama exclusiva testing; estas pruebas no aplican migraciones.
- `NEON_PRODUCTION_CONNECTION_STRING`: API en entorno `Production`; prohibido usarla en desarrollo o pruebas.
- Exigir `Ssl Mode=VerifyFull`, hostname verificable y certificado confiable. Para migraciones y pruebas de sesión usar endpoint directo (sin `-pooler`). No imprimir las variables ni habilitar logs de parámetros sensibles.
- Para cambios nuevos, verificar explícitamente rama y endpoint directo Testing y revisar el SQL generado antes de migrar. No ejecutar `database update` sobre Development/Production sin autorización específica.
- Fase 7: `RADIOMOVIL_MIGRATION_TARGET=testing`, `NEON_TESTING_BRANCH=testing` y conexión directa de Testing explícita. El modelo de Identity se aplicó solo allí.
- Las pruebas usan Testing exclusivamente; no refrescar ni reemplazar la rama Testing con Production.
- Si falta la variable testing, las pruebas Neon se muestran como omitidas: esto no verifica la migración ni PostgreSQL.
- Pruebas reales 3.3: ejecutar solo con `NEON_TESTING_DIRECT_CONNECTION_STRING`, `NEON_DEVELOPMENT_DIRECT_CONNECTION_STRING`, `NEON_PRODUCTION_CONNECTION_STRING` y `NEON_TESTING_BRANCH=testing` establecidos desde fuentes seguras; las pruebas rechazan hosts coincidentes. Nunca cargar una URL de production como testing. La rama `testing` se creó solo con esquema desde `development`, sin copiar filas; después de validar tablas/FKs/índices/PostGIS se registró la migración inicial en su historial (Neon schema-only no clona esas filas). Se aplicó la migración adicional `AislamientoYExclusividad` **solo en testing**. La prueba de esquema vacío crea y elimina exclusivamente un esquema `rm_test_<GUID>` en testing.
- Los tests de escritura usan IDs aleatorios y pueden dejar filas de prueba en la rama testing. No ejecutar en bases compartidas. Las migraciones no se aplicaron en production ni en development en esta fase.
- Fase 7 (API): rutas de negocio solo si `ASPNETCORE_ENVIRONMENT=Testing`, conexión y `NEON_TESTING_BRANCH=testing` configuradas; requieren cookie web o Bearer Android de Identity. Se retiró `X-Test-Api-Key`. El cliente mantiene `Idempotency-Key` en escrituras y usa la empresa seleccionada en el login, validada contra su membresía; nunca concede privilegios a IDs del cuerpo. No publicar Testing en internet.

Esto no demuestra capacidad de producción. Neon Testing requiere migración `AislamientoYExclusividad`; no ejecutar esta API sobre Development sin migrarla y autorizarlo previamente.
- Fase 4.1: `NeonConcurrencyBenchmarks` es opt-in (`RM_RUN_BENCHMARK=1`), exige las URL de Testing directa y agrupada (`NEON_TESTING_DIRECT_CONNECTION_STRING`, `NEON_TESTING_POOLED_CONNECTION_STRING`), `NEON_TESTING_BRANCH=testing` y `RM_BENCH_OUTPUT` fuera del repositorio. La ejecución usó comparadores de host sentinela sin conectarse a otras ramas; se verificó que ambas URL se extrajeron explícitamente de Testing y comparten endpoint/base/usuario. Solo prueba 1/5/10; `RM_BENCH_20=1` prueba 20 en una ejecución **posterior**. Hace calentamiento y dos repeticiones por nivel, verifica persistencia, claves, orden y reintenta las claves de respuestas inciertas. `Server-Timing` (solo rutas autenticadas en Testing) y JSONL de métricas contienen nombres/tiempos de etapas, no secretos. El observador usa conexión directa de Testing para `pg_stat_activity` y `pg_blocking_pids`; su muestreo no sustituye tiempos exactos de lock. No instalar `pg_stat_statements` automáticamente si falta.
- Línea base (2×100 por modo/nivel): directo 1/5/10 = 200/200 respuestas 201 por nivel; agrupado 1/5 = 200/200, agrupado 10 = 198/200. Las dos respuestas 500 NO estaban persistidas antes del reintento; cada una produjo 201 al repetir exactamente su clave. Contador medio directo 182/2463/5256 ms para 1/5/10; conexión caliente <0,1 ms; p99 directo a 10 entre 23,9 y 24,6 s. `pg_locks` detectó esperas sobre `transactionid` durante el UPSERT del contador y `SAVEPOINT` de EF bajo ese bloqueo. `pg_stat_statements` no instalado. El nombre `application_name` no se refleja en `pg_stat_activity` para algunas sesiones agrupadas: cero muestras de locks NO significa ausencia de bloqueo.
- Cambio contrastado de fase 4.1: en el registro de una sola llamada a `SaveChanges` se omite el savepoint automático solo durante esa llamada; ante cualquier error se abandona la transacción completa sin commit y se restaura la opción del DbContext. HTTP 201 nuevo se construye con los datos ya confirmados tras COMMIT, evitando un SELECT que antes podía fallar después de confirmar. Reintentos 200 siguen leyendo el registro original. No se tocan índices, bloqueos, timeouts ni orden.
- Contraste final Fase 4.1: tras ese cambio, 2×100 por modo/nivel para c1/5/10: 1200/1200 HTTP 201, persistidas y con claves únicas; medias directas 600/1476/2748 ms, agrupadas 526/1383/2721 ms. Después se hizo c20: 2×100 directas y 2×100 agrupadas, 400/400 HTTP 201 y persistidas, p99 entre 19 y 25 s; el observador (por usuario de Testing, no solo application_name) contó ~1300–1383 muestras de bloqueo por repetición. El límite de 30 s sigue cerca: no extrapolar a producción. Test de FK huérfana en `SaveChanges` verificó rollback de contador, solicitud e idempotencia; 31/31 tests finales aprobados. Los resultados JSONL quedan fuera del repositorio en el directorio temporal de OpenCode, sin claves ni contraseñas. Diferencias entre ejecuciones pueden incluir variación de RTT y compute; no se midió el stage preciso de la prueba histórica c20.
- Fase 5: migración `DespachoManualIdempotente` crea exclusivamente `operaciones_despacho` con clave `(EmpresaId, Ambito, Clave)`, huella del contenido y resultado histórico; DDL revisado y aplicado **solo en Testing**. Para herramientas EF dirigidas a Testing: `RADIOMOVIL_MIGRATION_TARGET=testing`, `NEON_TESTING_BRANCH=testing` y `NEON_TESTING_DIRECT_CONNECTION_STRING` de la rama testing explícita. Nunca ejecutar `database update` apuntando a development/production en esta fase. Reintentos se serializan por índice y devuelven el resultado guardado; errores revierten transacción completa. Bloqueo de solicitud `FOR UPDATE`, `clock_timestamp()` tras adquirirlo, ofertas/viajes protegidos por índices/triggers existentes y eventos + Outbox en el mismo COMMIT. EF mantiene savepoints por defecto aquí; la excepción de Fase 4.1 sigue limitada al registro de solicitudes.

- Fase 6.1: migración `WorkersRecuperacion` revisada (tabla `incidencias_worker`, índices) y aplicada SOLO a Neon Testing. Workers `BackgroundService` se registran únicamente en host Testing y con `RADIOMOVIL_WORKERS_ENABLED=1`, `RADIOMOVIL_WORKER_ACTOR_ID` GUID no vacío. `RADIOMOVIL_WORKERS_BATCH_SIZE` (1–100, predeterminado 16) e `RADIOMOVIL_WORKERS_INTERVAL_SECONDS` (mín. 1, predeterminado 5) son configurables. Sin opt-in no se activan. No son proceso independiente: requieren host Testing activo.
- `OfferExpirationWorker`: escaneo con reloj PostgreSQL, VencerAsync y clave `worker-expire:{id}`; bloqueos/índices del despacho aseguran exclusividad. `RecoveryWorker` reintenta incidencias `VencimientoFallido` con próximo intento persistido y máximo 5 intentos; si no pudo persistir la incidencia por indisponibilidad de DB, el siguiente escaneo redetecta la oferta. `ReconciliationWorker` alerta contradicciones e idempotencias incompletas, NO reinterpreta pendientes antiguas. Alertas abiertas: `SELECT * FROM incidencias_worker WHERE "AtendidaEn" IS NULL`; tras reparación, marcar atendida o reactivar intento de forma controlada. Las operaciones Fase 5 son atómicas: no hay leases caducados de despacho ni trabajo confirmado parcialmente que recuperar. Una caída posterior al COMMIT se resuelve releyendo el estado.
- Fase 6.2 bloqueada: no se encontró configuración de RabbitMQ y TCP 127.0.0.1:5672 no fue accesible. `IOutboxTransport` es solo contrato; no se registran publisher ni consumidor ni se marcan eventos publicados.
